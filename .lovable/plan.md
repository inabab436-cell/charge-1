# نظام تسوية فلوس الشحن (بوسطة)

الهدف: التاجر يفتح الصفحة فيعرف فورًا: فلوس إيه اللي وصلت، إيه اللي لسه، وإيه اللي وصل ناقص وكام بالظبط — من غير أي شغل يدوي.

## المبدأ الأساسي
النظام لا يكرر شغل التاجر، بل يعمل حاجة واحدة صعبة عليه يدويًا:
مقارنة ثلاث طبقات لكل أوردر:
1. المبلغ المطلوب تحصيله (من الأوردر عند التاجر)
2. المبلغ اللي بوسطة قالت إنها حصّلته (حالة الشحنة)
3. المبلغ اللي وصل فعلًا في التحويل البنكي (كشف التسويات)

الفرق بين 1 و2 = مشكلة تحصيل. الفرق بين 2 و3 = رسوم أو خصم أو نقص. الرسوم المتوقعة تتحسب من جدول أسعار التاجر، فأي فرق زائد يتعلّم عليه ويظهر كتنبيه.

## المرحلة صفر: التأكد من بيانات بوسطة (أول خطوة فعلية)
قبل أي بناء، نتحقق من الـ API بحساب تجريبي أو مفتاح من التاجر ونجاوب على:
- هل بيرجّع قيمة COD المحصّلة لكل شحنة؟
- هل بيرجّع الرسوم المخصومة لكل شحنة؟
- هل بيرجّع رقم/تاريخ التحويل البنكي (payout) اللي الشحنة اتسددت فيه؟
- هل فيه خانة reference للأوردر بترجع مع الشحنة؟
- هل فيه webhook لتغيّر الحالة، ولا لازم نسحب كل فترة؟

النتيجة تحدد المسار:
- الـ API يغطي التحويلات → كل شيء آلي.
- لا يغطيها → الحالات من الـ API، والمبالغ المحوّلة من ملف التسويات اللي بوسطة بتبعته (رفع بالسحب والإفلات، والنظام يقرأه ويطابقه لوحده).

مخرج هذه المرحلة تقرير مكتوب بما هو متاح فعلًا، وبناءً عليه نثبّت التفاصيل.

## الربط بين الأوردر والشحنة (بدون مجهود من التاجر)
مطابقة متدرجة تلقائية، وأول قاعدة تنجح تُعتمد:
1. رقم التتبع لو موجود في بيانات الأوردر.
2. رقم الأوردر المرجعي من خانة reference في بوسطة.
3. رقم الموبايل + المبلغ في نافذة زمنية معقولة.
4. رقم الموبايل + الاسم + قرب التاريخ.

القواعد 1 و2 تُعتمد آليًا. القواعد 3 و4 تظهر في صفحة "يحتاج تأكيد" كاقتراح بضغطة واحدة، والنظام يتعلّم من التأكيد فلا يسأل عن نفس التاجر/النمط مرة تانية. أي شحنة بلا أوردر، أو أوردر بلا شحنة، يظهر في قائمة منفصلة بدل ما يضيع بصمت.

## مصادر الأوردرات
- رفع ملف Excel/CSV: النظام يقرأ الأعمدة ويخمّن معناها (رقم الأوردر، الموبايل، المبلغ، رقم التتبع) ويعرضها للتأكيد مرة واحدة، ويحفظ التخطيط للمرات القادمة.
- شوبيفاي: ربط اختياري يسحب الأوردرات تلقائيًا لمن يستخدمه.
كلا المصدرين يصبّان في نفس جدول الأوردرات، فباقي النظام لا يفرّق بينهما.

## جدول الأسعار
التاجر يدخل مرة واحدة: سعر الشحن حسب المنطقة، نسبة/رسوم تحصيل COD، رسوم المرتجع. منه نحسب "صافي متوقع" لكل أوردر، والمقارنة تصير برقم محدد بدل إحساس عام.

## الشاشات
- لوحة رئيسية: إجمالي محصّل، إجمالي وصل، إجمالي منتظر، إجمالي ناقص — بأرقام قابلة للنقر.
- قائمة الأوردرات بفلاتر: وصلت مضبوطة / وصلت ناقصة / لسه / مرتجع / غير مطابَقة.
- صفحة الأوردر: الأرقام الثلاثة جنب بعض مع سبب الفرق وتاريخ التحويل.
- صفحة التسويات: كل تحويل من بوسطة والأوردرات اللي بداخله ومجموعها.
- صفحة "يحتاج انتباهك": المطابقات المقترحة والفروق غير المفسّرة فقط.

## التفاصيل التقنية
- التطبيق على Lovable Cloud (قاعدة بيانات + حسابات + كود خادم) مع عزل بيانات كل تاجر.
- جداول: التجار، الأوردرات، الشحنات، التحويلات، بنود التحويل، جدول الأسعار، قواعد المطابقة المتعلَّمة، سجل الاستيراد.
- مفاتيح بوسطة وشوبيفاي تتخزن مشفّرة وتُستخدم من الخادم فقط.
- كل مبلغ يتخزن بوحدة القروش (أعداد صحيحة) لمنع أخطاء التقريب.
- الاستيراد فريد لكل أوردر/شحنة، فإعادة رفع نفس الملف لا تكرر أي بيانات.
- سجل تدقيق لكل تغيّر مبلغ أو حالة، فأي رقم قابل للتفسير.

## ترتيب التنفيذ
1. التحقق من قدرات بوسطة API (المرحلة صفر).
2. الأساس: حسابات + استيراد ملف الأوردرات + جدول الأسعار.
3. سحب الشحنات من بوسطة ومحرك المطابقة.
4. التحويلات والمقارنة الثلاثية وصفحة الفروق.
5. اللوحة الرئيسية والفلاتر.
6. ربط شوبيفاي الاختياري.
